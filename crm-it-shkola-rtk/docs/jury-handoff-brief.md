> знать о проекте, чтобы написать презентационное/сопроводительное описание
> решения (одностраничник, питч-документ, README для жюри — что попросят).
> Ниже — факты и формулировки, проверенные и актуальные на момент хакатона;
> компоновать в финальный документ (структуру, тон, длину) — по запросу того,
> кто это читает.

## 1. Контекст и постановка задачи

Хакатон-кейс ЛЦТ (Летний Цифровой Трек / аналог), дедлайн **29.09.2026
23:59**. Домен: **CRM для ИТ Школы Ростелекома** — внутренний инструмент,
автоматизирующий полный цикл взаимодействия ИТ Школы с вузами-партнёрами: от
первого контакта до продления/завершения лицензии на ИТ-продукт.

Проблема, которую решает продукт: сейчас процесс работы с вузами (кто с кем
на какой стадии, у кого истекает лицензия, где зависла заявка) ведётся
вручную/разрозненно — нет единой точки видимости ни у менеджера, ни у
руководителя, ни у администрации. Решение — CRM с явным workflow-графом
статусов, ролевой видимостью данных и автоматическим радаром рисков (лицензии
на исходе, просроченные SLA) без каких-либо ML-моделей — только прозрачные
SQL-правила по датам.

## 2. Роли и бизнес-логика

Три роли, вложенные по зоне видимости: **КАМ ⊂ команда Руководителя ⊂ всё,
что видит Администратор**. RBAC проверяется не только в UI, а на уровне
каждого запроса к бэкенду (`CatalogScopeInterceptor`, общий для каталогов,
workflow и отчётов).

| Роль | Видит | Может |
|---|---|---|
| **КАМ** (менеджер по вузам, ~20 человек в реальной команде) | Только свои вузы и взаимодействия по ним | Вести взаимодействие: создать процесс, перевести по статусам workflow, прокомментировать переход, приложить файл (например, подписанный договор), править заметку/продукт своего взаимодействия |
| **Руководитель** | Все вузы своей команды КАМов + вузы без ответственного («ничьи», требуют внимания) | Переназначать ответственного КАМа за вуз; видит процесс, но **не двигает статусы за КАМа** (только просмотр) |
| **Администратор** | Всё без ограничений | Полный CRUD каталогов (вузы, ИТ-направления/продукты, вендоры, ответственные лица, лицензии), импорт вузов из xlsx, редактирование workflow-шаблонов (с версионированием), управление пользователями/ролями, запуск синхронизации с внешней системой (мок LMS/сайта) |

## 3. Ядро продукта — workflow взаимодействия

- **Шаблон процесса** («Типовой цикл внедрения ИТ-продукта») — редактируется
  Администратором.
- **Версионирование шаблона**: редактирование НЕ мутирует текущую версию, а
  создаёт новую; существующие взаимодействия остаются на своей версии, пока
  их явно не перенесут — история прошлых процессов не «переписывается
  задним числом» при изменении процесса.
- **Статус** — шаг процесса: название, одна из **7 CLM-макростадий**
  (Инициация → Переговоры → Партнёрство → Внедрение → Обучение →
  Сопровождение → Завершение), норматив SLA в днях, минимальная длительность
  и зависимости от других статусов (для расчёта критического пути на
  фронте — вкладка «Критический путь» в реестре).
- **Переход** — разрешённое ребро графа «из статуса A в статус B». Это
  единственный источник истины «можно ли сделать такой переход»: сервер
  всегда проверяет граф (400-ошибка, если перехода нет в шаблоне), точечное
  редактирование карточки **намеренно не может** менять статус в обход этой
  проверки.
- **История** — append-only журнал: кто, когда, из какого статуса в какой,
  комментарий, опциональное вложение. Ничего не удаляется и не
  перезаписывается — это аудиторский след процесса.
- Взаимодействие может завестись вручную (КАМ/Админ) или прийти из
  интеграции с внешним источником заявок (см. §6) — во втором случае, если
  система не смогла однозначно сопоставить курс из заявки с ИТ-продуктом,
  заявка помечается «требует проверки» и ждёт ручного разбора Руководителем
  или Администратором, а не сопоставляется вузу автоматически.

## 4. Killer-фича — радар лицензий, SLA и health score

Три виджета одного дашборда на одних и тех же данных, **без единой ML-модели
— только прозрачные правила по датам**, что специально ценно для домена
(объяснимость важнее точности):

- **Радар лицензий** — сколько лицензий истекает в окнах ≤7 / ≤30 / ≤60 дней
  или уже просрочены.
- **Радар SLA** — какие взаимодействия зависли на текущем статусе дольше
  норматива этого статуса.
- **Health score вуза** — свёртка обоих сигналов плюс «застой» активности и
  число заявок, требующих проверки, в единый цвет (красный/жёлтый/зелёный) и
  число 0–100 на вуз, с готовыми текстовыми причинами (не просто цифра —
  видно, почему именно так). Веса и пороги вынесены в конфиг, легко
  перенастраиваются без изменения логики.

## 5. Стек и технические решения

- **Backend**: NestJS + TypeScript, Prisma ORM + PostgreSQL, Redis (кэш GET-
  ответов и очередь BullMQ под отчёты), Garage — S3-совместимое хранилище
  файлов (в терминах контракта — «MinIO-совместимое»), Keycloak (OIDC) для
  боевой авторизации, Swagger/OpenAPI на весь контракт.
- **Dev-авторизация**: заголовок `X-Dev-Role: kam|rukovoditel|administrator`
  вместо реального логина — переключается флагом `AUTH_MODE`, без гибридной
  логики (либо целиком dev, либо целиком Keycloak).
- **Frontend (прототип)**: статические HTML-компоненты на собственном
  dc-runtime (без сборки/бандлера), общий API-клиент `crm-data.js` с
  автоматическим fallback на встроенные демо-фикстуры, если бэкенд
  недоступен (индикатор источника данных виден в интерфейсе и в консоли).
- **Единая схема ошибок API**: `{ code, message, details? }` на весь бэкенд —
  ни одного эндпоинта с произвольным форматом ошибки.
- **Обновления через PATCH**, без полной перезагрузки сущности на каждое
  точечное изменение.
- Комментарии в коде — только на неочевидных местах бизнес-логики (почему,
  а не что), без обфускации.

### Масштаб бэкенда (актуально на дату хакатона)

- **18 доменных сущностей** в схеме БД (User, University, License,
  WorkflowTemplate/Version/Status/Transition, InteractionInstance,
  StatusHistoryEntry, FileAttachment, CourseMapping, IntegrationSyncRun,
  ImportJob, AuditLog и др.).
- **10 контроллеров, ~79 REST-эндпоинтов**, полностью описанных в
  Swagger/OpenAPI (`/api/docs`, `/api-json`).
- Нефункциональные требования, под которые проектировался бэкенд: отклик
  API < 1с на переходах/фильтрации, 50 параллельных пользователей, 10
  параллельных отчётов без деградации (отсюда — асинхронная очередь отчётов
  через BullMQ, а не блокирующие запросы).

## 6. Интеграция с внешней системой (мок LMS/сайта)

Отдельный, явно задокументированный ограниченный контур — не скрытая
заглушка, а осознанная граница мока: в реальности источник заявок — сайт/LMS
ИТ Школы, сейчас — статичная JSON-фикстура вместо HTTP-вызова (структура
входа идентична тому, что будет на реальном контуре). Дедупликация — по
номеру заявки, повторный запуск синхронизации не плодит дублей. После
попадания в CRM заявка дальше живёт по тем же правилам, что и вручную
заведённое взаимодействие (тот же workflow-граф, та же история, те же
отчёты и радары) — интеграция не создаёт «параллельный», отдельно живущий
домен данных.

## 7. Архитектура backend (модули NestJS)

| Модуль | Что делает |
|---|---|
| `catalogs` | Вузы/направления/продукты/вендоры/лицензии + импорт xlsx. Здесь же общий `CatalogScopeInterceptor`, который считают видимость по роли — переиспользуется `workflow` и `reports`, а не дублируется |
| `workflow` | Шаблоны/версии/статусы/переходы, инстансы взаимодействий, append-only история. Единственное место, где проверяется граф переходов |
| `reports` | Реестр/графики/экспорт, радары лицензий/SLA, health score, асинхронная очередь отчётов (BullMQ) |
| `files` | Загрузка/скачивание вложений через S3-совместимое хранилище — контент стримится через backend (не прямой презайн-линк на хранилище — так решение работает из любого браузера, а не только изнутри Docker-сети) |
| `integrations` | Мок-адаптер LMS/сайта — см. §6 |
| `auth` | Идентификация (dev-заголовок или Keycloak JWT), управление пользователями/ролями, RBAC-guard на всё приложение |
| `health` / `observability` | `/health` (пинг Postgres/Redis/хранилища/Keycloak), `/metrics` (Prometheus), structured JSON-логи без персональных данных |
| `cache` | Redis-кэш GET-эндпоинтов каталогов/дашборда, сброс по namespace при любой записи |
| `common` | Единая форма ошибок на весь API |

Полная диаграмма компонентов (PlantUML C4 + Mermaid) — в
`docs/architecture.md`; пошаговый план и полный список эндпоинтов — в
`docs/backend-plan.md`.

## 8. Деплой и инфраструктура

- **Docker Compose**: Postgres, Redis, Garage (S3), Keycloak, backend — весь
  стенд поднимается одной командой (`docker compose up -d`), миграции и
  первичный сид демо-данных — автоматически при старте контейнера.
- **Домен**: `itschool-rtk-supremum.ru`, DNS уже указывает на боевой сервер.
- **HTTPS**: nginx как единая точка входа (терминация TLS, отдача статики
  фронтенда + проксирование API), сертификат — Let's Encrypt через certbot с
  автопродлением. Backend и Keycloak после этого смотрят только на
  `127.0.0.1` — снаружи доступны исключительно через nginx.
- **Сервер**: Timeweb Cloud VPS (2 vCPU / 4 ГБ RAM / 20 ГБ SSD), выбран
  как бюджетный вариант под нагрузку стека (Keycloak + Postgres + Redis +
  Garage + backend одновременно).

## 9. Тестирование перед деплоем

Перед выводом на боевой сервер проведён полный ручной прогон «от угла до
угла» по всем трём ролям на реальном бэкенде (не на демо-фикстурах):
дашборд/радар, реестр (таблица/доска/критический путь), карточка
взаимодействия с историей и вложениями, переход статуса, генерация отчётов,
управление командой/ответственными, административные каталоги,
workflow-редактор, матрица видимости данных, техпросмотр состояния сервисов.

В ходе тестирования найдены и устранены три дефекта до деплоя на боевой
сервер:
1. Формирование отчётов было синхронным (блокирующим) вместо асинхронного
   через очередь, как того требует ТЗ — переведено на реальный `POST
   /reports/jobs` + опрос статуса.
2. Селектор стадии CLM в редакторе workflow-шаблонов был невидим на узких
   экранах (баг CSS Grid) — исправлено.
3. Ссылки на скачивание файлов (отчёты и вложения) были подписаны на
   внутренний Docker-хост хранилища и не открывались бы из реального
   браузера — переведено на стриминг файла через сам backend.

## 10. Известные ограничения (честно, для прозрачности перед жюри)

- Интеграция с LMS/сайтом — мок на статичной фикстуре (см. §6), контракт
  входа спроектирован под реальное подключение, но реального HTTP-вызова
  пока нет.
- Формат экспорта отчёта PDF — реализован (рендер через pdfkit с шрифтом,
  поддерживающим кириллицу); xls/xlsx — основной, наиболее протестированный
  путь.
- Keycloak используется как OIDC-провайдер, но для демо/жюри включён
  `AUTH_MODE=dev` (вход по кнопкам ролей без реального логина) — ради
  скорости показа; переключение на боевой логин — вопрос одной переменной
  окружения, доменная модель/RBAC не меняются.
