# CRM ИТ Школа РТК — план бэкенда и синхронизация с фронтом

_Обновлено: 26.09.2026_

## Обзор

CRM-система для ИТ Школы Ростелекома — автоматизация полного цикла взаимодействия с вузами: от поиска контакта до сопровождения обучения преподавателей и контроля лицензий на ИТ-продукты. Задача — сократить трудозатраты КАМов за счёт прозрачных статусов, SLA и отчётности (кейс ЛЦТ, дедлайн 29.09.2026, 23:59).

Killer-фича — радар лицензий и SLA: дашборд, который автоматически подсвечивает лицензии, истекающие в ближайшие 60/30/7 дней, и взаимодействия, зависшие на одном статусе дольше порога. Прямое попадание в цель ТЗ — «сокращение трудозатрат сотрудников».

Три роли: КАМ (~20 человек, видит свои вузы), Руководитель (видит команду, переназначает ответственных), Администратор платформы (каталоги, workflow-шаблоны, пользователи).

## Технологический стек

- Backend: NestJS + TypeScript — конвенциональная структура удобна для AI-ассистированной разработки, единый язык с фронтом на React.
- ORM/БД: Prisma + PostgreSQL.
- Очереди/кэш: Redis (BullMQ под асинхронную генерацию отчётов, кэш пользовательских действий).
- Файлы: S3-совместимое хранилище (Garage) под вложения к статусам workflow — клиент (npm-пакет `minio`) работает с любым S3-совместимым сервером, поэтому смена MinIO на Garage код не затронула.
- Auth: Keycloak (OIDC), три роли из ТЗ.
- Документация API: Swagger/OpenAPI (`@nestjs/swagger`), контракт фиксируется до начала фронтенд-разработки.
- Инфраструктура: Docker Compose — весь стенд одной командой на Linux.

## Финальный функциональный скоуп (MVP)

| Модуль | Содержание |
| --- | --- |
| Каталоги и импорт | Вузы, ИТ-направления, ИТ-продукты, вендоры, ответственные, лицензии/договоры; импорт xlsx с настраиваемым маппингом полей, превью, дедуп/фаззи-матчинг по названию вуза |
| Workflow | Шаблоны (статусы + переходы), версионируемые; статусы сгруппированы в 7 CLM-макростадии; редактор шаблона — список/форма (граф — стретч); история переходов append-only с комментарием и вложением |
| Отчёты | Фильтры по периоду/вузу/направлению/продукту/ответственному; экспорт xls/xlsx/pdf; 2-3 базовых графика (pie/line/bar) |
| Killer-фича | Радар лицензий и SLA на дашборде + фильтр «только просроченные» в реестре |
| Интеграции | Отдельный модуль-адаптер под LMS и сайт: интерфейс + мок-реализация с реалистичными JSON-фикстурами; полный цикл запрос → JSON → создание/обновление без дублей; в документации явно указано, что контракт принят самостоятельно |
| Auth & RBAC | Keycloak, 3 роли, разграничение видимости данных по роли |
| Технические обязательные | Swagger на все эндпоинты, единая схема кодов ошибок, Redis-кэш + частичные обновления без reload, structured logs + /health + счётчики, Docker Compose, экспорт сущности/отчёта в JSON |

## Коды ошибок

Единый формат ответа на любую ошибку: `{ "code": string, "message": string, "details"?: any }`. `message` — человекочитаемый текст на русском для отображения "как есть". `details` заполнено только у `VALIDATION_ERROR` (массив `{field, errors[]}`). Коды ниже сгруппированы по областям; `uiHint` указан там, где фронту стоит обработать код отдельно, а не просто показать `message`.
